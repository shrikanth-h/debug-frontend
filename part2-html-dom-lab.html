03Edit HTML live

Three ways to edit, and one myth to kill.

Original title

Double-click my text. Then try F2 on the whole element.

Try this
  1. Edit a text node — double-click the heading's text and retype it.
  2. Edit one attribute — double-click the class attribute in the Elements tree and change it.
  3. Edit the whole element — select the outer div and press F2 (Edit as HTML). Paste a whole fragment; Ctrl+Enter commits it. Right-click → Edit as HTML opens the same editor.
  4. Now the myth: double-click the heading's text again and, while it is in edit mode, read the element's attributes in the tree. There is no contenteditable anywhere.
The three edits, and how to reach each one
1. A text node — double-click the text
2. One attribute — double-click the attribute name or its value
3. The whole element, as HTML — select the node→F2 or right-click the node→ Edit as HTML — two routes, one editor
Every edit dies on reload. Capture a diff first: ⋮ More options→ More tools→ Changes

The myth: DevTools does not add contenteditable to edit text. That attribute is an authoring feature for your visitors — unrelated to inspector editing.

06Selected element $0

$0 is not one fixed element — it always points at whatever is highlighted in the Elements tree right now.

Element A — #dollar-first. Select me first.
Element B — #dollar-second. Select me second.
Try this — part 1: what $0 is
  1. Inspect Element A (the purple box).
  2. Press Esc to open the drawer. The drawer remembers whichever tab you used last, so if it shows Issues or Search, click the Console tab inside the drawer. Keeping Elements visible above means you can see what $0 is pointing at.
  3. Run $0 — DevTools echoes the element back.
  4. Run $0.id — "dollar-first". Proof of what it points at.
  5. Run $0.dataset — {sku: "SKU-42", tier: "gold"}
  6. Run $0.getBoundingClientRect() — its real measured position.
  7. Run $0.style.outline = '4px solid red' — you just restyled it from the Console.
Try this — part 2: why the numbers go up to $4
  1. Element A is still selected, so $0.id is "dollar-first".
  2. Now click Element B (the green box) in the Elements tree.
  3. Back in the Console, run these two lines:
    $0.id → "dollar-second"   (B — the new selection)
    $1.id → "dollar-first"   (A — pushed down one slot)
  4. Select a third element anywhere on the page and run all three: $0.id, $1.id, $2.id. Everything has shifted down again.

So $0–$4 is a five-deep history of your selections. $0 is the current one; $1 the one before; $4 the oldest DevTools still remembers. Each new selection pushes the others down and drops the sixth. Useful when you need to compare two elements without losing the first.

Try this — part 3: the $ and $$ helpers
  1. Run $$('.ord'). You get an array of three <a> elements — the three reorder links from section 04 of this page, which carry class="ord". Nothing magic about .ord; it is just a CSS class that exists on this page.
  2. Because it is a real Array, you can chain straight onto it:
    $$('.ord').map(el => el.textContent.trim())
  3. Compare with the standard DOM call:
    document.querySelectorAll('.ord').map(el => el.textContent)
    That throws — a NodeList has no .map(). This is the practical reason $$ exists.
  4. Run $('.ord') — the first match only.

These exist only in the DevTools Console. Put $0 or $$() in your page's JavaScript and it throws ReferenceError. And if the page loads jQuery, the page's $ wins over the DevTools one — but $$ and $0 keep working.

Capture node screenshot is on the outer menu, not in the Copy submenu. It sits low down, between Switch to accessibility tree and Scroll into view — which is why it is easy to miss while you are looking at Copy.
Try this — all seven Copy options
Everything below assumes the selected node is #copy-me.
  1. Copy element and Copy outerHTML — both give you the element's full HTML, the opening tag included. Paste each into a text editor and compare; treat them as the same tool.
  2. Copy selector → #copy-me — a CSS selector. Paste it inside document.querySelector('…') in the Console to prove it resolves.
  3. Copy JS path → document.querySelector("#copy-me") — the same selector, already wrapped and runnable. Paste straight into the Console, or into a Playwright or Cypress test.
  4. Copy styles — the element's CSS rules as text, for pasting into a stylesheet or a bug report.
  5. Copy XPath → //*[@id="copy-me"] — the short XPath, anchored to the id.
  6. Copy full XPath → something like /html/body/div/section[9]/div/div — the absolute path from the root. Brittle: it breaks the moment anything above it moves.
  7. Capture node screenshot (outer menu) — saves a PNG of just this element to your downloads. Ideal for a bug ticket.

Which one to reach for: JS path for anything you are going to run or automate. Selector when you need the string alone. XPath when no CSS selector can express the target — an attribute-value match, or "the element containing this text". Avoid full XPath except as a last resort.

Why it matters on a real app: hashed class names change every build. Copy selector gives you something that works right now.

09Event listeners

Including the one that is not on the element you clicked.

This container has a delegated click listener. The button has three of its own.

no events yet
Try this — part 1: prove what is attached (never fails)
  1. Press Esc for the Console. Run this — it names the element explicitly, so it does not depend on what is selected:
    Object.keys(getEventListeners(document.getElementById('listen-btn')))
    → ['click', 'focus', 'mousedown'] — three.
  2. Now the container, same way:
    Object.keys(getEventListeners(document.getElementById('delegate-parent')))
    → ['click'] — one. That single one is the delegated listener.
  3. Have DevTools select the button for you, so no clicking accuracy is needed:
    inspect(document.getElementById('listen-btn'))
    The Elements panel jumps to that node and $0 now is the button.
  4. Confirm it: $0.id → "listen-btn". Then Object.keys(getEventListeners($0)) → all three.
The most common wrong result — and its one-line fix
If getEventListeners($0) returns just {click: Array(1)}:
That is one click listener on the selected node — the signature of the container, not the button. Nothing is broken; $0 is simply pointing at div#delegate-parent.
Fix it in one line: inspect(document.getElementById('listen-btn')) then run getEventListeners($0) again.
Why it happens: the button sits inside a dashed container. Clicking anywhere in the padding around the button — or right-clicking near it and choosing Inspect — selects the container. inspect() sidesteps that entirely.

Do part 1 before touching the pane. These commands name their element explicitly, so their answer is the truth. If the pane then disagrees, the pane is being read wrong — not the page.

The five-second check: press Esc and run $0.id in the Console. It must print "listen-btn". If it prints "delegate-parent", you are on the container.
In the Elements tree the row you want reads <button class="listen-btn" id="listen-btn">. Clicking the dashed area around the button selects the container instead — click the green button itself, or the button's own row in the tree.
Try this — part 2: reading the Event Listeners pane
  1. Inspect the green button, confirm $0.id is "listen-btn", then open the Event Listeners sidebar tab.
  2. The pane groups by event type, not one row per listener. With the button selected you get three collapsed rows, alphabetically: click, focus, mousedown.
  3. Still short of rows? The pane is a small scrolling area — scroll inside it or widen DevTools. And press the ↻ refresh button at the pane's top-left; it does not always repopulate on its own after you change selection.
  4. Click the ▸ on a row to expand it. The individual listeners live inside the type row, each with its target node and a source:line link.
  5. Now tick Ancestors and expand click again. It gains a second entry, div#delegate-parent — the delegated listener, inherited from up the tree.
  6. Untick Ancestors and it disappears again. That toggle is the whole lesson.

The asymmetry: DevTools has privileged access, so a closed shadow root hides nothing from you as a debugger — but it does hide it from page JavaScript.

Exact path Elements→ sidebar tab strip (behind » if narrow)→ Accessibility
The pane has three parts: Accessibility Tree, ARIA Attributes, and Computed Properties — the last one holds the computed name, role and states.

Why this is the right last card: the accessibility tree is the browser's final answer about your HTML. An empty name on an icon button is a WCAG failure you cannot see by looking at the page.
