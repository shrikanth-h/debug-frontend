DevTools Essentials Lab

A working exercise for every card in Part 1 — the twelve everyday DevTools features.

Part 1 is about the toolbox rather than the page, so this lab's job is to trigger things: real requests, real console traffic, real browser-reported issues.

Open this over http(s), not by double-clicking the file. On file:// the browser treats the page as a unique null origin, so sections 03, 09, 10 and 12 behave oddly or show nothing. Use the GitHub Pages URL, or run python -m http.server in the folder and open http://localhost:8000/.

04Docking

Docking is not cosmetic — it changes the viewport you are debugging.

Try this
  1. Dock left or right and watch the box change from WIDE to NARROW.
  2. Dock bottom and it returns to WIDE.
  3. Undock into a separate window — the page gets its full width back.
Exact path ⋮ More options→ Dock side→ left / bottom / right / undock
or press Ctrl+Shift+D to cycle.

The trap: a right-docked DevTools can silently put you below a breakpoint, so you debug a "bug" that only exists because your viewport shrank.

06Console drawer

Something has to be logging while you are looking elsewhere.

stopped
Try this
  1. Click Start heartbeat logging. It logs one line every two seconds.
  2. Open the Console panel and watch the beats arrive.
  3. Now switch to the Elements panel. The Console is replaced — you can no longer see them.
  4. Press Esc. The drawer opens underneath Elements with Console inside it, and the beats are visible again while you keep inspecting.
  5. Press Esc again to close it. Stop the heartbeat when you're done.

Where it earns its keep: stepping through breakpoints in Sources while watching what your code logs, without losing your place by switching panels.

09Reload modes

The difference shows in one column of the Network panel.

navigation type: reading…
no assets requested yet
Try this
  1. Open the Network panel and click Load three cacheable assets — now the request list has something in it.
  2. Find the Size column. If you cannot see it, see the box below.
  3. Reload normally (Ctrl+R) and click the button again. Cached responses read (memory cache) or (disk cache) instead of a byte count.
  4. Now, with DevTools open, right-click the browser's reload button (the circular arrow next to the address bar — not anything inside DevTools). Three options appear: Normal reload, Hard reload, Empty cache and hard reload.
  5. Run the third. The Size column fills with real byte counts — everything re-downloaded.
Can't see the Size column? Right-click any column header→ tick Size
The header row is Name · Status · Type · Initiator · Size · Time · Waterfall. Right-clicking it toggles columns. If the panel is narrow (docked bottom in a short drawer), later columns are clipped — widen it or dock to the side.
On file:// there is no HTTP caching, so this section only works over http(s).

The diagnosis: "it works after a hard refresh" is not a fix. It means your cache headers or asset hashing are wrong, and returning users are on the stale copy.

10Preserve log

A real navigation, so you can watch the console get wiped — or not.

current page: A
Try this
  1. With preserve off, click the button. It logs three lines then navigates — and the console is wiped before you can read them.
  2. Turn it on using either path below.
  3. Click again. The pre-navigation logs survive, separated by a navigation divider.
Two separate settings — the Console and the Network panel each have their own
Console: Console panel→ ⚙ settings gear (right of the Console toolbar)→ Preserve log
Network: Network panel→ checkbox in the top toolbar
Chrome's documentation calls it Preserve log. Recent builds label the Network one Keep log — same control, renamed. If you see "Keep log", that is the one.
Needs http(s): on file:// Chrome blocks this navigation ("'file:' URLs are treated as unique security origins").

Non-negotiable for: login redirects and OAuth hops. The request that caused the redirect only exists in the log you preserved.

11Settings & the Ignore List

A fake vendor library, so you can watch a stack trace get shorter.

The trace runs: your handler → vendor-lib.js → your callback.
Try this
  1. Click the button, then expand the stack trace in the Console. You will see three frames, with vendor-lib.js in the middle.
  2. Add vendor-lib to the Ignore List using the exact path below.
  3. Click the button again. The vendor frame is gone; only your code remains.
  4. To undo it, return to the same pane and remove the pattern.
Exact path to the Ignore List ⚙ Settings (gear, top-right of DevTools — or press F1) → Ignore List (left sidebar of the Settings dialog) → tick "Enable Ignore Listing" → Custom exclusion rules → Add pattern… → type vendor-lib → Add
This pane was called Blackboxing until Chrome 106 — that is why older articles send you somewhere that no longer exists. It already ships with /node_modules/ and /bower_components/ ignored by default.
Faster route once you know it: right-click the vendor-lib.js frame in the Console stack trace and look for Add script to ignore list. The Settings path above always works; the context-menu entry is not offered for every script type.

On a real app: ignore-list React, your bundler runtime and vendor chunks. Stack traces stop being forty frames of framework and start pointing at your code.

Three ways to open Issues
1. Fastest — click the ⚑ issue counter, top-right of the DevTools toolbar
2. Menu — ⋮ More options→ More tools→ Issues
3. Command Menu — Ctrl+Shift+P→ type "Issues"
Once open, Issues lives in the drawer beside Console, so Esc brings it back afterwards.
On file:// the CORS failure still fires (origin null), but you also get unrelated file: security noise. http(s) is cleaner.

Start here, not in Console. For CORS, cookies, deprecations and mixed content, Issues names the cause and the fix. The Console just says something failed.
