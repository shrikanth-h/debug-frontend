Console & Logging Lab

A working exercise for every card in Part 4, getting more out of the Console than console.log().

Nearly every section here writes to the Console, so keep it open the whole way through. Read the map below first. One default setting silently hides a third of what this page logs.

01Log levels

Five methods, four levels, and one of them is hidden by default.

Nothing fired yet.
Try this
  1. Open the Console and click Fire all five levels. Count what you see. Most people get four lines, not five.
  2. The missing one is console.debug(). Open the level dropdown (it reads Default levels) and switch to All levels, or tick Verbose. If the dropdown is greyed out and reads Custom levels, the console sidebar is open. Close it with the first toolbar icon, or click verbose in the sidebar instead.
  3. Fire again. Now there are five.
  4. Untick everything except Errors. Only console.error() survives.
  5. Note that console.log() and console.info() both land under Info. They are the same level, not two.
The mapping
MethodLevelShown by default?
console.debug()Verbose No
console.log() / console.info()InfoYes
console.warn()WarningsYes
console.error()ErrorsYes

Why it matters: use the levels and the filter starts working for you. A noisy app becomes readable by switching to Errors only. Log everything at Info and you have thrown that away.

02Structured logging

The same event, logged two ways. Both are searchable. Only one is reliable.

Both write to the Console. Compare what you can do with them.
Try this
  1. Click both of the first two buttons and look at the Console. The object is expandable; the sentence is not.
  2. In the filter box, type checkout. Both lines match. The filter is a plain text search over what the Console renders, and that includes the one-line preview of an object. So a word search alone is not where structured logging wins.
  3. Now type req-7f3. The object matches, the sentence disappears. Nobody wrote the request ID into the sentence. Prose holds only what the writer remembered to mention; an object with a fixed shape carries every field, every time.
  4. Type /step: 'checkout'/ (slashes make it a regex). Only the object matches. The sentence says "checkout page", but it has no step field to match against. A word can appear anywhere; a field means one thing.
  5. Click Log 6 events, then filter by req-7f3 again. You get just that request's events, across different steps of the flow.
How the filter actually matches It tests the text the Console displays for each line, not the object in memory. For an object, that is the collapsed preview, so a field that falls outside a long, truncated preview will not match. Keep the fields you search on near the front of the object.

Where this grows up: put the same correlation ID in the browser log that your gateway puts in its trace. A support ticket stops being "it broke on checkout" and becomes one request you can follow end to end, across the browser, the BFF and every service behind it. The bigger payoff is downstream: a log pipeline can query correlationId = "req-7f3" exactly, which no amount of searching prose can do.

03console.table()

The best thing in the Console for API responses.

Output goes to the Console.
Try this
  1. Click Table the full array. Note the leading (index) column. For an array that is 0, 1, 2, separate from the objects' own id field.
  2. Click a column header to sort by it. Not obvious, and very useful.
  3. Click Table only two columns. That is console.table(data, ['name','status']). Wide API rows become readable.
  4. Click Table an object of objects. Now (index) holds the keys instead of numbers.
  5. Right-click the table → Copy table to paste it into a ticket.

04Group related logs

Collapse a whole workflow into one line.

Output goes to the Console.
Try this
  1. Clear the Console first (Ctrl+L) so older lines do not get in the way.
  2. Click Log an open group. The header reads "starts OPEN" and its two lines show straight away, with a ▼ arrow.
  3. Click Log a collapsed group. A new header appears reading "starts CLOSED", with a ▶ arrow and nothing under it. Click the arrow to reveal its three lines.
  4. If you clicked both, the first Checkout group in the Console is the open one. Read the header text, not the position, to tell them apart.
  5. Click nested groups to see a checkout flow three levels deep.
  6. Every console.group() needs a matching console.groupEnd(). Miss one and everything logged afterwards stays trapped inside your group.

Use console.groupCollapsed() by default for anything routine. An expanded group for a flow that runs on every page load is just noise with an arrow on it.

05Measure time

Real durations, without opening the Performance panel.

idle
Try this
  1. Click Run a timed three-stage task and watch the Console. You get two intermediate console.timeLog('checkout') readings and one final console.timeEnd('checkout') total.
  2. The label string ties the three calls together. Click End a timer with a typo. It calls console.timeEnd('chekout'), one letter off, and Chrome warns Timer 'chekout' does not exist. Nothing was measured, and in a real app the warning is easy to miss among other logs.

console.timeLog() is the underused one. It prints the elapsed time without stopping the timer, so you can mark stages inside one operation and see which stage actually costs you.

06Trace execution

"How did we even get here?" answered in one line.

idle
Try this
  1. Click the button. The trace arrives already expanded (▼), under your label "trace: who called addToCart?". It shows with Default levels, no dropdown change needed.
  2. It is a flat list, one frame per line in the form name @ file:line, not a nested tree. Read it top down: the innermost function first, each caller below it. addToCart, then updateCart, then handleClick.
  3. The last line, (anonymous), is the button's click handler that started the chain. Anonymous functions show up exactly like that, which is one reason to name them.
  4. Click any file link on the right to open that line in Sources.
  5. With no argument, console.trace() labels the entry console.trace. Passing a string, as this page does, makes one trace easy to find among many.

Where it beats a breakpoint: when a function is called from many places and you need to know which caller is responsible, without stopping execution each time.

07Assert & count

Two APIs that stay quiet until they matter.

idle
Try this
  1. Click assert with a TRUE condition. Nothing appears. That is correct. An assert logs only when the condition is false.
  2. Click the FALSE one. Now you get an error-level line with your message.
  3. Click console.count('render') five times. It prints render: 1 … render: 5.
  4. Click countReset. It prints nothing at all. Then count again: back to render: 1.
  5. Now reload the page and click countReset FIRST, before ever counting. This time it does speak up: Count for 'render' does not exist, at warning level. Resetting a counter that exists is silent; resetting one that never existed is not.

console.count() is the cheapest re-render counter in React. One line inside the component body: no state, no extra render caused by the measurement itself, and you get a hard number instead of an argument about whether memoisation works.

08Log vs dir

Same element, two completely different outputs.

idle
Try this
  1. Click Log it and dir it. In the Console you get the same button twice: console.log() renders it as markup you can expand like the DOM tree; console.dir() renders it as an HTMLButtonElement property bag, with disabled, innerText, [[Prototype]] and the rest.
  2. Expand the console.dir() output and find dataset. It holds {sku: "SKU-42"}, a thing you cannot read off the markup view.
  3. Select the button in Elements, then run both by hand: console.log($0) and console.dir($0).
  4. Now click the same to a plain object. The two outputs are near identical, because a plain object has no markup representation to differ from.

The rule: the distinction only exists for DOM nodes. Reach for console.dir() when you want properties such as event handler flags, dataset, value versus attribute, the prototype chain. Reach for console.log() when you want to see structure.

09Filter & search logs

Four filter modes, and one that is not a filter at all.

idle
Try this
  1. Click the button. Twenty lines arrive, some from this page, some from an injected vendor-analytics.js.
  2. Plain text: type checkout in the filter box.
  3. By source: type url:vendor-analytics. Only the third-party noise. Then -url:vendor-analytics with a minus to exclude it and see only your own logs. That minus is the one people never learn.
  4. Regex: type /SKU-\d+/ to match any SKU.
  5. Search, not filter: clear the box, then press Ctrl+F. That searches what is already printed and highlights hits without hiding anything else.
Filter vs search, different jobs
Filter boxCtrl+F
Hides everything that does not match. Live, so new logs are filtered too. Highlights matches in what is already there. Nothing is hidden.

-url: is the one to remember on a real site. Third-party tags produce most of the console noise, and excluding them by source is faster than trying to describe your own logs.

10Style log output

%c applies CSS to everything that follows it.

All output goes to the Console.
Try this
  1. Click each button and read the Console. The code each button runs is in the box below, ready to paste.
  2. %c consumes the next argument as a CSS string and applies it to everything after that point in the message.
  3. The badge example resets styling with a second %c and an empty string. That is how you stop a style bleeding into the rest of the line.
  4. The last button shows %s (string), %d (integer), %f (float), then logs the Buy button from section 08 twice: %o shows it as markup, %O as a property bag.
  5. Paste snippet 5 into the Console, then call logCart("hello"). That helper is the one worth keeping.
Syntax you can paste into any Console Every button above runs one of these. Copy a line into the Console on any site and it works.
1. One styled label
console.log("%cPAYMENT", "color:#c00; font-weight:bold; font-size:14px");
2. A badge, then plain text (the empty string resets the style)
console.log("%c CHECKOUT %c order #4120 created",
  "background:#2E9E63; color:#fff; font-weight:bold; border-radius:3px; padding:2px 6px",
  "");
3. Several %c segments, one style argument each, in order
console.log("%cred %cgreen %cblue",
  "color:#c00; font-weight:bold",
  "color:#2E9E63; font-weight:bold",
  "color:#2F6FE0; font-weight:bold");
4. The other format specifiers
console.log("string %s | integer %d | float %f", "SKU-42", 7, 12.3456);

const btn = document.querySelector("#buy-btn");
console.log("%o", btn);   // a DOM node, shown as markup
console.log("%O", btn);   // the same node, shown as a JS object

%s string, %d or %i integer (decimals are dropped), %f float, %o element as markup, %O always as a JS object, %c CSS.

5. Day-to-day: a reusable tagged logger
const tag = (name, bg) => (...args) =>
  console.log(`%c ${name} `, `background:${bg}; color:#fff; border-radius:3px`, ...args);

const logCart = tag("CART", "#2E9E63");
const logPay  = tag("PAYMENT", "#c00");

logCart("item added", { sku: "SKU-42", qty: 2 });
logPay("authorised", { orderId: 4120 });

Define it once near the top of a module. Every line from that subsystem then carries the same badge, and objects after the label stay expandable.

Use it sparingly, for labels only. One coloured badge marking which subsystem a line came from is genuinely useful. A rainbow console is harder to read than a plain one, and none of it survives being copied into a ticket.

11Live expressions & utilities

Watch a value change without logging it on a loop.

cart.items.length = 0
window.cart is a real global. Inspect it from the Console.
Try this
  1. Click the 👁 eye icon in the Console toolbar to create a live expression. Type cart.items.length and press Enter.
  2. It pins above the console and updates on its own as you click Add and Remove. No logging, no loop.
  3. Add a second live expression: cart.total.
  4. Now the utilities. Type each one at the Console prompt (see the box below): copy(cart) puts the whole object on your clipboard as JSON; monitorEvents($0, 'click') logs every click on the selected element (unmonitorEvents($0) stops it); inspect(document.getElementById('buy-btn')) jumps Elements to that node.
  5. $_ returns the last expression's value, handy after a long chain.
Where the "utilities" live There is no Utilities panel, menu or button. They are functions Chrome adds to the Console prompt only, officially called the Console Utilities API. To use one:
Console tab, or Esc for the drawer→ click the > prompt at the bottom→ type copy(cart) and press Enter
The full list is in Chrome's docs under "Console Utilities API reference" (developer.chrome.com/docs/devtools/console/utilities).

12Logging hygiene

The card that is not about convenience.

Recorder is off. Start it, then click the other two.
Try this
  1. Click Start a fake session recorder. It wraps console.log() the same way a session-replay or error-monitoring SDK does. A few lines of code, nothing exotic.
  2. Click Log a token the careless way. Look at the capture box: the bearer token and the password are now sitting in the recorder's buffer.
  3. Click Log it the safe way and compare. Same debugging value, nothing sensitive.
  4. In a real app that buffer is uploaded to a third party. Nothing in the Console warns you.

This is the part most people underrate. "Don't log passwords" reads as obvious advice everyone has internalised. The non-obvious half is that console output does not stay in your browser. Session-replay and error-monitoring tools capture it by default, so a token you logged "just to check" leaves your origin and lands in someone else's storage, under their retention policy rather than yours.

Practical rule: log identifiers, not identities. An order ID, a correlation ID and a user role are all safe and all useful. An email address, a token or a full name is none of those things.
