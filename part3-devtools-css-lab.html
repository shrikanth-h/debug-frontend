DevTools CSS Debugging Lab

A minimal reproduction for every card in Part 3, plus the three additions from the comments.

Open DevTools (F12) and work down the page. Every section is built so the feature you are looking for is actually present — which is the thing a real production site cannot promise.

01Styles pane

Every matched rule, editable in place.

Inspect me.
Try this
  1. Right-click the blue card → Inspect.
  2. In Styles, hover a declaration — a checkbox appears to its left. Untick border.
  3. Click the #EAF1FE swatch and drag inside the colour picker; the page updates live.
  4. Click any numeric value and press ↑/↓ to step it. Shift+↑ steps by 10.

Where: Elements → Styles.

02Cascade & specificity

Three rules set color on one button. Two lose.

Try this
  1. Inspect the button. Read the Styles pane top to bottom — that is cascade order, winner first.
  2. Find the two struck-through color declarations.
  3. Untick the winning #spec-target rule; the next one down comes alive. Untick that too and the grey type selector finally applies.
  4. Click the source link on the right of any rule to jump to it in Sources.

Answer: #spec-target (1,0,0) beats .spec-btn (0,1,0) beats button.spec (0,0,1). Source order never enters into it — specificity settles it first.

Where: Elements → Styles.

03Inheritance

The child declares nothing. It still has a colour and a font.

I am the parent and I set color, font-family and font-style.

I am the child. I declare nothing. Inspect me.

Try this
  1. Inspect the child paragraph.
  2. Scroll the Styles pane down to the Inherited from div.inherit-parent section.
  3. Note what appears there and what does not. The parent also sets border and padding, but those are not inheritable, so they never show up.

The point: you never write color: inherit for this to happen. Inheritance is the default for text-ish properties; the inherit keyword is for forcing the ones that aren't.

Where: Elements → Styles, below the element's own rules.

04Computed styles

rem, %, em and ch go in. Pixels come out.

Every length on me is relative.
Try this
  1. Inspect the box, open the Computed tab, tick Show all.
  2. Filter for padding. The declared 0.75em is reported in px.
  3. Expand the arrow beside a computed property — it names the rule that set it, with a source link.
  4. Change font-size in Styles and watch padding and line-height move with it, because em and unitless line-height are relative to it.

Where: Elements → Computed.

08Force element state

The card that is impossible to demonstrate without DevTools.

Try this
  1. Inspect the button. Click :hov in the Styles toolbar.
  2. Tick :hover — the style holds even with your mouse elsewhere.
  3. Now tick :focus-visible. The amber ring pins open so you can measure its contrast. This is the only way to audit a focus indicator — the moment you click into DevTools, real focus leaves the button.
  4. The full list is :active :hover :focus :focus-within :focus-visible :target.

Where: Elements → Styles → :hov.

09CSS variables & the silent fallback

One token resolves. One is misspelled — and nothing complains.

var(--brand-color) — resolves
var(--brand-colour, #9ca3af) — misspelled, fallback wins
Try this
  1. Inspect the blue box and hover var(--brand-color) — the resolved value appears.
  2. Inspect the grey box. Same syntax, no error anywhere, and the design token was simply ignored.
  3. Open Computed on the grey box: it reports the fallback grey as fact.
  4. Edit :root in Styles and add --brand-colour:#16a34a. The grey box turns green.

The point: a mistyped design token is not an error. It is a slightly wrong colour that ships. The resolved value is the only place it becomes visible.

Where: Elements → Styles and Computed.

11Animations panel

A 4-second infinite animation — long enough to actually catch.

Try this
  1. Command Menu (Ctrl+Shift+P) → Show Animations.
  2. The running animation is captured as a group. Click it to open the timeline.
  3. Set speed to 25% or 10%, then drag the playhead to scrub.
  4. Drag the keyframe markers to retime it live, then read the changed values in Styles.

Where: the Animations panel, in the drawer.

12CSS Overview, Coverage & Changes

Three different tools that people conflate. This page feeds all three.

#b9b9b9 on white — fails WCAG AA, and CSS Overview knows it.

I am an inline span with width, height and margin-top that do nothing.
Try this
  1. Command Menu → Show CSS Overview → Capture overview.
  2. Open Contrast issues — the grey paragraph is listed with its ratio.
  3. Open CSS declarations / unused declarations — the inline span is there, because width, height and margin-top do not apply to a non-replaced inline element.
  4. Now for rules that match nothing: Command Menu → Show Coverage, reload, and read the unused-bytes bar. That is where .never-matched-* shows up.
  5. Edit a few styles anywhere on this page, then Command Menu → Show Changes for a red/green diff you can paste into your editor.

The distinction that trips people up: CSS Overview's "unused declarations" means declarations that have no effect on the element they are on. Selectors that match nothing are a different problem, and Coverage is the tool for those.

Where: CSS Overview, Coverage and Changes are all separate drawer tools.

13@layer — the missing card

An ID selector losing to a class selector, legitimately.

Inspect me. Am I red or green?

And I am styled by an unlayered rule.

Try this
  1. Inspect the first paragraph. Styles now groups rules under @layer base and @layer utilities.
  2. The cascade-layers control appears in the Styles toolbar — open it to see the declared layer order.
  3. #layer-target — an ID — is struck through, beaten by .layer-box p, purely because utilities is declared after base.
  4. Inspect the second paragraph: its unlayered rule wins over everything layered.

Answer: green. Layers are compared before specificity, so specificity only breaks ties within a layer. That control only appears when the page actually uses @layer — which is why you will never find it on a site like Amazon.

Where: Elements → Styles.

14Stacking context — z-index 9999 that loses

One cause, one checkbox, instant fix.

I have z-index: 9999
I have z-index: 2 — and I win
Try this
  1. Inspect the red box. It really does have z-index:9999.
  2. Inspect its parent .sc-parent. Its only declaration is opacity:0.99 — visually almost nothing, and it creates a stacking context.
  3. Untick opacity. The red box jumps to the front immediately.
  4. Open the Layers panel (Command Menu → Show Layers). Note that it shows compositing layers — related, but not the same thing. Chrome has no first-class stacking-context inspector.

Why it earns a card: the fix is never in the element you are inspecting. opacity below 1, transform, filter, will-change, contain, isolation:isolate, position:fixed and a non-auto z-index on a positioned element all create one, silently. If several are present at once, unticking one changes nothing — which is exactly what makes this bug so frustrating in real code.

Where: Elements → Styles, then the Layers panel for context.

15Container queries

Drag the handle at the container's bottom-right corner.

I respond to my container
Try this
  1. Drag the resize handle past 420px. The item turns green — the viewport never changed.
  2. Inspect the item: Styles shows the @container card (min-width:420px) block, greyed out when it does not match and active when it does.
